# ติดตามเปลี่ยนถ่าย: ระยะ 1 Local Demo

> อัปเดตตามโจทย์ล่าสุด: แถบในเมนูรถเปลี่ยนเป็นอ่านทะเบียน Feet และไมล์ HR-POS จริง
> แบบ read-only แล้ว ดู `docs/oil-current-mileage.md` ส่วนหน้าสาธิตแยกยังคงใช้คู่มือนี้

## สถานะและขอบเขต

ยังไม่ใช่ระบบบันทึกจริง และยังไม่ Deploy ไม่มีการอ่าน/เขียน Supabase,
ไม่เชื่อม HR-POS ไม่ส่ง LINE ไม่ดึงวันที่แจ้งซ่อมมาตั้งเป็นวันเปลี่ยนถ่าย
ไม่เปลี่ยนขั้นตอนใบซ่อม สต็อก PO หรือการอนุมัติเดิม

โค้ดเดิมที่ใช้เป็นแนวทาง: `page_buses.html`, เมนูรถและสิทธิ์ Admin ใน `Js.html`,
โปรแกรม S/M/S2/L ใน `page_oiltemplate.html`, custom signed sessions ใน
`functions/auth-utils.js`, และรูปแบบผู้ทำรายการ/เวลา/อ้างอิงใน stock/LINE logs
โมดูลใหม่เก็บ audit ของตนเอง ไม่เขียนปะปนกับ stock_logs หรือ line_logs

## วิธีลองอย่างปลอดภัย

```powershell
npm run local:oil
```

เปิด URL ที่ terminal แสดง ปกติ `http://localhost:5190/oil-tracking-demo.html`
ถ้าพอร์ตไม่ว่างจะลองพอร์ตถัดไปถึง 5210 ตัวเซิร์ฟเวอร์นี้ bind เฉพาะ loopback
และให้บริการเฉพาะไฟล์หน้าสาธิต ไม่โหลด `.env` ไม่เปิด API/function ของแอปจริง
ไม่ต้องล็อกอินบัญชีจริง ไม่ต้องติดตั้งตาราง และไม่มีคีย์ Supabase ในหน้าสาธิต

หลังเปิด Local ของแอปเดิม เลือก **จัดการรถบัส → ติดตามเปลี่ยนถ่าย**
แท็บนี้อ่านทะเบียนและไมล์จริงแบบ read-only ตามคู่มือฉบับใหม่ ไม่ใช้ Demo
เมนูอื่นของแอปเดิมยังเชื่อมระบบจริงตามการตั้งค่าเดิมอยู่
จึงแนะนำใช้ `local:oil` สำหรับทดสอบที่ไม่แตะระบบจริงโดยเด็ดขาด

ทุกหน้ามีป้าย Local Demo ปุ่มบันทึกและข้อความยืนยันระบุว่าเป็นข้อมูลสาธิต
เลือก Admin / User / Manager จำลองได้ในหน้าสาธิตแยก
ในแท็บของแอปเดิมใช้บทบาทผู้ใช้ที่ล็อกอินอยู่ และไม่มีตัวเลือกเปลี่ยนบทบาท

## ขั้นตอนทดลอง

1. ค้นหาทะเบียน กรอง 5 สถานะ และลองเปลี่ยนหน้าหรือจำนวนต่อหน้า
2. ดูประวัติรถ `30-1002 สข` ซึ่งยังไม่มีวัน/ไมล์ตั้งต้น
3. กดบันทึกเปลี่ยนถ่าย ใส่วันที่เปลี่ยนจริง เลขไมล์ โปรแกรม S/M/S2/L
   เลขอ้างอิงใบซ่อมกรอกเองได้หรือเว้นว่าง แล้วกรอกหมายเหตุถ้ามี
4. บันทึกไมล์ปัจจุบันพร้อมวันที่อ่าน ต้องไม่น้อยกว่าไมล์เปลี่ยนถ่าย
5. กลับตารางเพื่อดูไมล์และวันที่ครบกำหนด ระยะ/วันคงเหลือ และสถานะ
6. แก้รายการในหน้าประวัติโดยระบุเหตุผล ระบบเพิ่มฉบับใหม่และเก็บฉบับเดิม
   รายการต้นฉบับไม่ถูกลบหรือแก้ทับ ฉบับแก้ไขอ้าง `supersedes`
7. ใช้ปุ่มตั้งรอบเพื่อปรับกิโลเมตร/เดือนของแต่ละกลุ่ม และเกณฑ์เตือน
8. เปิดประวัติผู้ทำรายการเพื่อดูผู้ใช้ เวลา ข้อมูลก่อน/หลัง และเหตุผลแก้ไข
9. ลอง User หรือ Manager จำลอง: ดูและส่งออกข้อมูลได้ แต่บันทึก/แก้ไขไม่ได้

ตัวอย่างอื่น: `30-5115` ใกล้ครบ, `30-5456` ครบระยะ,
`30-1999` รอตั้งประเภทรถ, `30-1003` ไมล์ลดลง,
`30-1004` ไมล์เก่าต้องอ่านใหม่ ทุกทะเบียนและเลขใบซ่อมเป็นข้อมูลจำลอง

## กติกาคำนวณ

| กลุ่ม | รอบเริ่มต้น | ทะเบียนบังคับใช้ก่อนประเภทรถ |
| --- | --- | --- |
| รถบัสทั่วไป | 35,000 กม. / 6 เดือน | ไม่มี |
| รถบัสรอบพิเศษ | 20,000 กม. / 6 เดือน | 30-5115, 30-5145 |
| มินิบัส | 10,000 กม. / 6 เดือน | 30-5456, 30-5455 |
| รถตู้ปรับอากาศ | 10,000 กม. / 6 เดือน | ไม่มี |

กฎเฉพาะทะเบียนมีลำดับเหนือประเภทรถ แม้กรอกประเภทขัดกัน
รองรับทะเบียนตามด้วยจังหวัดที่คั่นด้วยช่องว่าง ไม่จับเลขบางส่วนของทะเบียนอื่น
ประเภททั่วไปต้องระบุเอง ไม่เดาจากยี่ห้อ รุ่น หรือหมายเลขป้าย
รถไม่ทราบประเภทจะรอตั้งต้น แม้มีประวัติครบ

- ไมล์ครบกำหนด = ไมล์เปลี่ยนจริงล่าสุด + รอบระยะทาง
- วันที่ครบกำหนด = วันเปลี่ยนจริงล่าสุด + เดือนปฏิทิน (วันที่ฐานแบบ AD/ISO)
- ตัวอย่าง 31 ส.ค. 2026 + 6 เดือน = 28 ก.พ. 2027;
  31 ส.ค. 2023 + 6 เดือน = 29 ก.พ. 2024 ไม่ใช้ 180 วัน
- ครบหรือเกินกำหนดเมื่อระยะคงเหลือ ≤ 0 **หรือ** วันคงเหลือ ≤ 0
- ใกล้ครบเมื่อเหลือ ≤ 2,000 กม. **หรือ** ≤ 30 วัน (ปรับได้)
- ปกติเฉพาะข้อมูลครบ ถูกต้อง และยังไม่อยู่ในช่วงเตือน
- รอตั้งต้นเมื่อไม่มีประเภทรถ ประวัติเปลี่ยนจริง หรือไมล์ปัจจุบัน/วันที่อ่าน
- ข้อมูลต้องตรวจสอบเมื่อวันผิด/อนาคต ไมล์ลดลง ไมล์ไม่สัมพันธ์กับวัน
  หรือข้อมูลไมล์เก่ากว่าเกณฑ์ (ค่าเริ่มต้น 30 วัน ปรับได้)
- กรณีมีความผิดปกติ ให้สถานะตรวจสอบก่อนสถานะรอตั้งต้น/ปกติ
- ไม่คาดการณ์อัตราวิ่งหรือคำนวณวันที่จากเลขไมล์
- ทุกโปรแกรม S/M/S2/L เริ่มรอบน้ำมันเครื่องใหม่เหมือนกัน
- ใช้วันที่ประเทศไทย `Asia/Bangkok` ในการประเมิน และคำนวณส่วนต่างวันแบบ UTC
  เพื่อไม่ให้ timezone/DST ทำให้คลาดเคลื่อน
- บันทึกย้อนหลังได้ถ้าไม่ทำให้ลำดับวันที่/ไมล์ขัดแย้ง
  บันทึกเปลี่ยนถ่ายใหม่ไม่ได้ปรับเลขไมล์ปัจจุบันให้อัตโนมัติ
  หากวันที่อ่านไมล์เก่ากว่าวันเปลี่ยนจริง ต้องอ่านไมล์ใหม่ก่อนแสดงปกติ

## การเก็บข้อมูลและข้อจำกัดของ Demo

เก็บ localStorage key `feet:oil-tracking:demo:v1` แยกจากข้อมูลระบบเดิม
ข้อมูลไม่แชร์ข้ามเครื่อง เบราว์เซอร์ หรือพอร์ต
กดดาวน์โหลดเพื่อสำรอง JSON ได้ ไม่มีการนำเข้าอัตโนมัติไปฐานข้อมูล
หากต้องเริ่มใหม่ ให้ส่งออกก่อน แล้วลบเฉพาะ key นี้จาก DevTools → Application
ไม่ใช้ Clear All เพราะอาจกระทบ session/ข้อมูลส่วนอื่น

Admin เท่านั้นเพิ่มประวัติ แก้ประวัติ กรอกไมล์ และตั้งกลุ่ม/รอบได้
User และ Manager ดูได้เท่านั้นตามแนว admin-only ของเมนูรถเดิม
สิทธิ์ใน Demo เป็นการจำลอง UI/store ไม่ใช่ขอบเขตความปลอดภัย production
ผู้ที่แก้ localStorage หรือ JavaScript เองสามารถแก้ข้อมูลจำลองได้
การเชื่อมจริงต้องตรวจ custom session และบทบาทซ้ำที่ server ทุกคำขอ

มี revision ป้องกันบันทึกจากหน้าจอที่ถือข้อมูลเก่า แต่ localStorage ไม่ใช่
transactional database และไม่รับประกัน concurrent writes หลายแท็บพร้อมกัน
เวลา/ผู้ใช้ audit ใน Demo มาจากเครื่องหรือบัญชีจำลอง จึงไม่ใช่หลักฐานทางธุรกิจ
ข้อมูลเดโมเก่าหรือเสียหายไม่ถูกรีเซ็ตทับอัตโนมัติ

## โครงสร้างฐานข้อมูลที่เสนอ (ยังไม่รัน)

ไฟล์ `sql/oil-tracking-phase1.DRAFT.sql` มี guard หยุดการรันทันที
เตรียม 6 ตารางใหม่เท่านั้น: รถที่ติดตามแบบ ID คงที่, รุ่นนโยบาย,
events เปลี่ยนถ่าย/อ่านไมล์แบบ append-only, audit, global revision และ request receipts
เปิด RLS และปิดการเข้าถึง anon/authenticated ทั้งหมด
เตรียม API และ RPC adapter แล้ว แต่ endpoint ของแอปปกติยังปิด (503)
ไม่มี policy ฝั่ง browser เพิ่มเติม ไม่มี SQL แก้ตารางเดิม ไม่มี backfill จากใบซ่อม
ไฟล์ร่างมี INSERT เฉพาะ metadata revision 0 และค่าเริ่มต้นรอบเท่านั้น
ไม่มีข้อมูลรถ/ประวัติจริง และยังไม่ได้รันแม้แต่ SQL บรรทัดเดียว

ผลกระทบหากอนุมัติและใช้ภายหลัง: เพิ่มตาราง/ดัชนีและพื้นที่เก็บประวัติใหม่
ไม่ได้เปลี่ยน repairs, buses, stock, purchase_orders หรือ LINE
สคริปต์มี RPC transaction สำหรับบันทึก mutation+audit+receipt+revision พร้อมกัน
แต่ยังต้องรีวิวและทดลองจริงบน staging ก่อนใช้งาน ยังไม่ถือว่าผ่าน PostgreSQL integration test
รายละเอียด API และวิธีทดลองแยกอยู่ใน `docs/oil-tracking-api.md`

ก่อนรันจริงต้องได้รับอนุมัติจากเจ้าของระบบ รวมถึงยืนยันประเด็นต่อไปนี้:

1. รายชื่อและประเภทรถทั้งหมด พร้อมวัน/ไมล์เปลี่ยนจริงตั้งต้นที่ตรวจสอบได้
2. วิธีผูก stable vehicle ID กับ buses เดิมที่ใช้ป้ายทะเบียนเป็น primary key
   โค้ดแก้ทะเบียนเดิมมีการลบแล้วเพิ่มรถ จึงไม่เพิ่ม FK โดยพลการ
3. สิทธิ์จริงว่าจะให้ Manager/User บันทึกได้หรือไม่ (ปัจจุบัน admin-only)
4. วิธีแก้ไขเลขไมล์ผิด หรือเปลี่ยนเรือนไมล์จริง: ระยะนี้ไม่รองรับ reset meter
   และจะปฏิเสธเลขไมล์ลดลง ไม่ปรับแต่งตัวเลขให้ผ่านเอง
5. ตรวจรับ endpoint/transaction ที่เตรียมไว้ด้วย PostgreSQL staging จริง
   รวมถึงทดสอบสิทธิ์ DB, rollback, simultaneous writes, และการเพิกถอนสิทธิ์บัญชี
   แล้วจึงอนุมัติให้ต่อ RPC adapter และเปลี่ยน UI จาก Demo เป็น API
6. แผนสำรองข้อมูลและทดสอบ SQL ใน Supabase staging ที่ไม่ใช่โปรเจกต์จริง
7. ขั้นตอนอนุมัติ Deploy แยกต่างหาก หลังผ่านทดสอบจริงใน staging

## การทดสอบ

```powershell
npm run test:oil
npm run test:oil-api
node build.js
# ต้องมี Playwright ใน NODE_PATH หรือในสภาพแวดล้อมทดสอบ
node tests/oil-tracking-browser.test.js
```

browser tests ใช้เซิร์ฟเวอร์ `local:oil` (ค่าเริ่มต้น 5190)
เปลี่ยน URL ได้ด้วย `OIL_TEST_URL` ทดสอบหน้ารวมของแอปผ่าน route mocks
ที่อ่านไฟล์ build ในเครื่อง โดยไม่เปิด backend จริง
ครอบคลุม 4 กลุ่ม กฎเฉพาะทะเบียน ขอบเขต 2,000 กม./30 วัน/วันครบกำหนด
สิ้นเดือน leap year ข้อมูลขาด ไมล์ลดลง วันที่อนาคต/ไม่จริง อายุข้อมูลไมล์
ประวัติฉบับแก้ไข สิทธิ์ revision conflict และข้อมูลสาธิตเสียหาย
browser ตรวจ desktop และ 360/390/430/768px การบันทึก/แก้ไข ค้นหา กรอง
แบ่งหน้า และไม่ส่ง request ไป Supabase/LINE/API จริง

## ระยะถัดไป (ยังไม่ได้ทำ)

- ระยะ 2: Feet อ่านไมล์ผ่าน read-only API ของ HR-POS พร้อม mapping รถและแหล่งข้อมูล
- ระยะ 3: เชื่อมปิดงาน S/M/S2/L ทั้งเว็บ/LINE เพื่อยืนยันวัน/ไมล์เปลี่ยนจริง
  รองรับยกเลิกปิดงานและแจ้งเตือน โดยออกแบบ idempotency/rollback แยกก่อน

ยังไม่มีการเปลี่ยน workflow เดิมเพื่อเตรียมสองระยะนี้
