# ทะเบียน Feet และไมล์ล่าสุด HR-POS (Read-Only)

## การเปิดบน Netlify

- ตั้งค่าฝั่ง Server ของไซต์ `feetmanagement` ใน production: `HRPOS_SUPABASE_URL` และ `HRPOS_SUPABASE_SERVICE_ROLE_KEY` จากโปรเจกต์ HR-POS เท่านั้น
- ใช้ค่า Feet `SUPABASE_URL` และ server key ที่มีอยู่เดิม ทั้งสอง URL ต้องเป็นคนละโปรเจกต์
- จำกัดค่าลับไว้ใน Functions scope ไม่เพิ่มใน build.js, HTML หรือไฟล์ public และไม่ commit ไฟล์ .env
- ต้อง Deploy ใหม่หลังตั้งค่า Environment Variables และทดสอบด้วยบัญชี Feet ที่เข้าสู่ระบบแล้ว
- API อ่านเฉพาะคอลัมน์ที่กำหนดและปฏิเสธ transport ทุก method นอกจาก GET ไม่มีการเขียนหรือรัน SQL
- ถ้าตั้งค่าไม่ครบ/อ่านไม่สำเร็จ แสดงข้อผิดพลาด ไม่ใช้ข้อมูลจำลองแทน โหมดสาธิตและ API บันทึกยังไม่เปิดใช้งานจริง

โจทย์ล่าสุด: ใน **จัดการรถบัส → ติดตามเปลี่ยนถ่าย** แสดงทะเบียนปัจจุบันของ Feet
และไมล์กลับล่าสุดจาก HR-POS ไม่ใช่ทะเบียน/เลขไมล์ตัวอย่าง

## เปิดใช้งาน Local

1. ปิดหน้าต่าง server เดิม แล้วเปิด `run-local.bat` จากโปรเจกต์ Feet นี้อีกครั้ง
   ต้อง restart เพราะเพิ่มเส้นทาง read-only ใน `run-local.js`
2. เปิด URL ที่ terminal แสดง (ปกติ localhost:5173 แต่ถ้าพอร์ตไม่ว่างอาจเป็นเลขถัดไป)
3. เข้าระบบตามปกติ → จัดการรถบัส → ติดตามเปลี่ยนถ่าย
4. กดรีเฟรชเพื่ออ่านต้นทางใหม่ ไม่มี auto-refresh และไม่มีการเขียนข้อมูลต้นทาง

หน้าตัวอย่างแยก `oil-tracking-demo.html` ยังคงเป็นข้อมูลจำลองสำหรับทดสอบสูตร
ส่วนแถบในแอปปกติไม่อ่าน localStorage ของ Demo และไม่คัดลอกข้อมูล Demo เข้าระบบ

## แหล่งข้อมูลที่อ่าน

- Feet: `.env` และ `.env.local` ในโฟลเดอร์โปรเจกต์นี้ ใช้ตาราง `buses` เฉพาะ `plate`
- HR-POS: `.env` และ `.env.local` จากโฟลเดอร์ข้างเคียง `HR-POS FOR SUPPABASE`
  (`.env.local` มีลำดับเหนือ `.env` ตามรูปแบบ HR-POS)
- หากย้ายโฟลเดอร์ HR-POS ให้กำหนด `HRPOS_PROJECT_DIR` ฝั่ง server ก่อนเปิด Local
- ต้องเป็น Supabase คนละ URL มิฉะนั้นจะหยุด ไม่อ่านจากโปรเจกต์เดียวกันแทน
- HR-POS `vehicles`: `plate_no`, `vehicle_type` เท่านั้น
- HR-POS `clearance`: `row_id`, `clearance_code`, `job_no`, `vehicle_plate`,
  `return_date`, `odom_before`, `odom_after` เท่านั้น
- อ่านแบบแบ่งหน้าเพื่อไม่ติดข้อจำกัด 1,000 แถว ไม่มีการอ่านเงินเดือน/รายรับ/ค่าใช้จ่าย

คีย์ทั้งหมดใช้เฉพาะ server ไม่ส่งคีย์ HR-POS หรือ service-role ไป browser
transport ของ client ใหม่ปฏิเสธทุก method ที่ไม่ใช่ GET
endpoint ตรวจ custom signed session ของ Feet และอนุญาต Admin/User/Manager ให้อ่าน
ไม่มี POST/PUT/DELETE/RPC และไม่มีการแก้ไฟล์ HR-POS หรือ SQL

## การจับคู่และไมล์ล่าสุด

- แสดงเฉพาะทะเบียนใน Feet ไม่เพิ่มรถ HR-POS ที่ Feet ไม่มี
- จับคู่ทะเบียนเต็มก่อน โดย normalize ช่องว่างและรูปแบบ dash
- ใช้เลขทะเบียนหลักโดยไม่รวมจังหวัดได้เฉพาะกรณีจับคู่ได้หนึ่งคันชัดเจน
- หากจังหวัดขัดกันหรือทะเบียนหลักซ้ำหลายคัน ไม่รวมข้อมูลให้เอง
- หาก HR-POS ไม่มีแถวทะเบียน แต่ใบเคลียร์มีทะเบียนเต็มตรงกับ Feet จะอ่านใบเคลียร์นั้นได้
  โดยไม่เดาประเภทรถ
- เรียง `return_date` ล่าสุดก่อน จากนั้น `row_id` ล่าสุดสำหรับวันเดียวกัน
  ไม่ใช้วันที่กดเคลียร์บิล/วันที่สร้างแถว และไม่ใช้เลขไมล์สูงสุด
- แสดงวันที่กลับจากงานเป็นวันที่ของข้อมูลไมล์ ไม่อ้างว่าเป็นวันที่อ่านไมล์สดวันนี้
- ปุ่มที่มาไมล์แสดงใบเคลียร์/เลขงานและประวัติล่าสุดไม่เกิน 5 แถว
- เลขไมล์กลับ 0 ของ HR-POS ถือว่ายังไม่บันทึก ไม่ใช้เป็นไมล์ปัจจุบันที่ยืนยันแล้ว
- หากไมล์ลดลง วันที่อนาคต/ไม่จริง หรือข้อมูลเก่ากว่า 30 วัน จะแสดงต้องตรวจสอบ
- เมื่ออ่านต้นทางล้มเหลว ให้แสดง error และล้างตาราง ไม่ใช้ข้อมูล Demo หรือข้อมูลเก่าแทน

กลุ่มรอบอ่านจากชื่อประเภทรถ HR-POS ที่ตรง whitelist เท่านั้น
ชื่ออื่นที่ยังไม่รู้จักจะรอตั้งกลุ่ม ไม่เดาจากยี่ห้อหรือช่วงป้ายทะเบียน
กฎเฉพาะ 30-5115 / 30-5145 / 30-5456 / 30-5455 ยังคงมาก่อนประเภทรถ

## รอบล่าสุดและรอบถัดไปจากใบงาน (ตามที่ผู้ใช้ยืนยัน)

ผู้ใช้ยืนยันให้นำเลขไมล์/โปรแกรมจากใบแจ้งซ่อมสถานะ **เสร็จแล้ว** มาเป็นฐานคำนวณ
และยืนยันลำดับโปรแกรม **S → M → S2 → L → S** สำหรับรอบถัดไป
อ่านตาราง repairs เฉพาะ repair_no/date/plate/mileage/oil_program/repair_list/repair_summary/status
ไม่แก้ทับใบงาน ไม่เขียน maintenance events ใหม่ และไม่คัดลอกข้อมูลลงฐานข้อมูล
เมื่อใบงานเสร็จแล้ว/ยกเลิกปิดงานในระบบเดิม การกดรีเฟรชจะคำนวณจากสถานะล่าสุดอีกครั้ง

- จับคู่ทะเบียนโดย normalize ช่องว่างและตรวจจังหวัดเหมือนเดิม
- เลือกเฉพาะใบงานเสร็จแล้วล่าสุดตามวันที่ใบงาน แล้วใช้เลขใบงานเป็นตัวตัดสินเมื่อวันเท่ากัน
- งานกำลังซ่อม/รออะไหล่/รอดำเนินการยังไม่นับเป็นการเปลี่ยนถ่าย แม้ใหม่กว่า
- ไมล์ครบกำหนด = ไมล์ในใบงานเสร็จแล้วล่าสุด + รอบกิโลเมตรของกลุ่มรถ
- โปรแกรมถัดไปมาจากลำดับที่ยืนยัน ไม่เปลี่ยนตามว่าครบด้วยระยะทางหรือเวลา
- วันครบกำหนด = วันที่ใบงาน + เดือนปฏิทินของกลุ่มรถ
  **ระบบเดิมไม่ได้เก็บวันที่ปิดงานจริงแยก จึงระบุว่าเป็นวันที่อ้างอิงจากใบงานเสมอ**
- ไมล์ปัจจุบันยังมาจาก HR-POS เท่านั้น ไม่ใช้ไมล์ในใบซ่อมแทนไมล์ปัจจุบัน
- ถ้าใบล่าสุดเลขไมล์เป็น 0/ว่าง โปรแกรมไม่ระบุ หรือโปรแกรมขัดกับรายละเอียด
  จะแสดงข้อมูลต้องตรวจสอบ ไม่ข้ามไปใช้ใบเก่าอย่างเงียบ ๆ และไม่คำนวณครบกำหนดให้
- ข้อความโปรแกรม S1 เทียบเป็น S, PM เทียบเป็น M และ PS2 เทียบเป็น S2
  ใช้เพื่อตรวจความขัดแย้ง ไม่เขียนแก้ข้อมูลต้นทาง
- หากประเภทกลุ่มรอบยังไม่ทราบ จะไม่เดารอบรถบัสทั่วไป
- ปุ่มที่มาข้อมูลแสดงประวัติใบงานที่เสร็จแล้ว และแยกงานที่ยังไม่นำมาคำนวณ

ตัวอย่าง: 30-4955 ล่าสุด M ที่ 325,964 กม. → รอบถัดไป S2 ที่ 360,964 กม.
การบันทึกประวัติบำรุงรักษาแบบมีวันเปลี่ยนจริงแยกยังรออนุมัติโครงสร้าง/API ตามแผนเดิม
API บันทึก `oil-tracking` ยังคงปิดอยู่ ไม่มีการเปิดเป็น production โดยปริยาย

endpoint อ่านใหม่ `oil-current-mileage` ถูกเชื่อมเฉพาะ custom `run-local.js`
export handler สำหรับ Netlify คืน 503 เสมอ ยังไม่เปิดเชื่อมบนเว็บไซต์จริง
ยังไม่ Deploy และไม่มี LINE/งานปิดซ่อม/สต็อก/PO เปลี่ยนไป

## สรุปบนแดชบอร์ด

แดชบอร์ดหน้าใหม่มีส่วนเปลี่ยนถ่ายน้ำมันเครื่อง แสดงจำนวนครบ/เกินกำหนด ใกล้ครบ
ข้อมูลต้องตรวจสอบ รอตั้งต้น และปกติ ใช้สถานะที่คำนวณจาก endpoint เดียวกับเมนูรถ
จัดคู่กับงานซ่อมที่ต้องติดตาม โดยบนมือถือจะแสดงส่วนเปลี่ยนถ่ายก่อนรายการงานซ่อม
รายการสำคัญสูงสุด 3 คัน เรียงครบกำหนด → ใกล้ครบ → ต้องตรวจสอบ
พร้อมโปรแกรมถัดไป ไมล์/วันที่ครบกำหนด และปุ่มดูทั้งหมด
กดจำนวนเพื่อกรองตามสถานะ หรือกดลูกศรที่ทะเบียนเพื่อเปิดรายการคันนั้นในแถบติดตาม

ข้อมูลใช้ cache เฉพาะหน่วยความจำฝั่ง browser อายุไม่เกิน 60 วินาที แยกตาม session
และวันประเทศไทย ไม่เขียน localStorage/ฐานข้อมูลสำหรับ cache
คำขอที่กำลังอ่านพร้อมกันแชร์ครั้งเดียว เพื่อลดการอ่าน HR-POS ซ้ำ
ปุ่มรีเฟรชข้าม cache และไม่มี polling/auto-refresh
เมื่ออ่านไม่สำเร็จ ตัวเลขเป็น “—” และปิดปุ่มตัวกรอง ไม่แสดง 0 หรือแจ้งว่าปกติทั้งหมด

## ทดสอบ

```powershell
npm run test:oil-mileage
npm run test:oil-repairs
npm run test:oil-data
node build.js
# ใช้ NODE_PATH ของ Playwright ตามเครื่องทดสอบ
node tests/oil-tracking-browser.test.js
node tests/oil-dashboard-browser.test.js
```

unit tests ใช้ข้อมูลจำลอง ครอบคลุมจับคู่ซ้ำ/จังหวัดขัดกัน/ทะเบียนเต็ม/4 กลุ่ม
การเลือกวันล่าสุดแทนค่าสูงสุด วันที่และเลขไมล์ผิดปกติ สิทธิ์ และ GET-only
browser tests mock ต้นทางทั้งหมด และตรวจ UI desktop/mobile, ที่มาไมล์,
ค้นหา และกรณีต้นทางล้มเหลวไม่กลับไปใช้ Demo
ชุด repair tests ตรวจเงื่อนไขเสร็จแล้ว, ไมล์ 0, โปรแกรมขัดกัน, วงรอบ S/M/S2/L,
ระยะทั้ง 4 กลุ่ม, สิ้นเดือน, ไมล์ลดลง และการไม่ใช้ใบงานที่ยังไม่เสร็จ
การตรวจต้นทาง Local จริงทำเฉพาะ SELECT ผ่าน GET ไม่มี SQL หรือการเขียนข้อมูล
